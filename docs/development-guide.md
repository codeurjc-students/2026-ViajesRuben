## Introduction

TripMate is a web application with a **Single Page Application (SPA)** architecture. In an SPA, the browser downloads a single HTML page once, together with the JavaScript code of the client application. From then on, the client updates the view dynamically and exchanges data with the server through a **REST API** (JSON over HTTP), instead of requesting a new HTML page from the server for every interaction. This separates the user interface completely from the business logic and lets other clients (for example, a mobile app or the Telegram bot) reuse the same API.

The application has three parts that run as independent processes:

- **Client (frontend):** a React application that runs in the user's browser.
- **Server (backend):** a Spring Boot application that exposes the REST API and contains the business logic. It is designed as a modular monolith organized by domain, so that it can be split into independent services in TFG2.
- **Database:** a MySQL server that stores the application's data.

| Aspect                  | Description                                                                                                                                                                                                                                                           |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Type**                | Web SPA with a REST API backend (modular monolith)                                                                                                                                                                                                                    |
| **Technologies**        | Backend: Java 21, Spring Boot, Spring Security, Spring Data JPA, MySQL. Frontend: React, React Router, React Bootstrap, Recharts, TypeScript, Vite                                                                                                                    |
| **Tools**               | Visual Studio Code, Maven, npm, Docker, Postman, Git, GitHub                                                                                                                                                                                                          |
| **Quality control**     | Unit, integration and system tests for backend and frontend (JUnit, Mockito, Testcontainers, Rest Assured, Selenium, Vitest, Testing Library); test coverage (JaCoCo, Vitest); static code analysis (SonarQube Cloud); code style checks (Spotless, ESLint, Prettier) |
| **Deployment**          | One Docker image (Spring Boot serving the React application over HTTPS) published on DockerHub, run with Docker Compose next to MySQL (see [Deployment](#deployment))                                                                                                 |
| **Development process** | Iterative and incremental; Git with GitHub Flow; continuous integration with GitHub Actions; tasks managed with GitHub Issues and GitHub Projects                                                                                                                     |

## Technologies

Technologies used by the application at runtime.

### Java

Programming language of the backend. The project uses Java 21, the current long-term support (LTS) version.
https://www.java.com/

### Spring Boot

Framework for building Java applications with minimal configuration. In TripMate it provides the web server, the REST API controllers, dependency injection and the configuration of the application.
https://spring.io/projects/spring-boot

### Spring Data JPA

Spring module that simplifies data access with JPA (Java Persistence API). The application's entities are mapped to database tables, and repositories provide the database queries without writing SQL for the common operations.
https://spring.io/projects/spring-data-jpa

### Spring Security

Spring module for authentication and authorization. In TripMate it checks the JWT that comes in a cookie (OAuth2 resource server), loads the user on every request and protects the URLs by role (see [Security](#security)). Passwords are stored with BCrypt.
https://spring.io/projects/spring-security

### springdoc-openapi

Library that generates the OpenAPI specification of the REST API from the Spring controllers and serves an interactive Swagger UI to explore it.
https://springdoc.org/

### MySQL

Open-source relational database management system. It stores all the persistent data of the application.
https://www.mysql.com/

### React

JavaScript library for building user interfaces from reusable components. It is used to implement the SPA client.
https://react.dev/

### React Router

Routing library of the SPA: it maps every URL (`/trips`, `/trips/:id`, `/admin/users`...) to a screen and keeps the navigation history without reloading the page.
https://reactrouter.com/

### React Bootstrap

Bootstrap components rebuilt for React (grid, cards, alerts, forms, modals). Bootstrap is themed with the TripMate design tokens instead of its default look; see the [design system](design-system.md).
https://react-bootstrap.github.io/

### Recharts

Chart library for React, used for the spending charts of the trip page (I5). Its charts are declarative React components that draw SVG, so they fit the rest of the application and, unlike a canvas, their bars, lines and reference lines are real DOM elements that the Vitest tests can inspect. Its version is pinned in `package.json` (no `^`).
https://recharts.org/

### TypeScript

Typed superset of JavaScript used for all the frontend code. The compiler (`tsc`, in strict mode) checks the types before the build, and the types of the REST API data are defined in `src/types` to match the backend DTOs.
https://www.typescriptlang.org/

### Vite

Build tool and development server for the frontend. It serves the React application during development with instant reload and generates the optimized production build.
https://vite.dev/

## Architecture

### Deployment

TripMate has two deployment architectures: the development one, with three processes started by the developer, and the packaged one, with two containers. The processes and the protocols between them are the following.

**Development.** TripMate runs as three independent processes:

```mermaid
flowchart LR
  B["Browser<br/>React SPA<br/>(Vite dev server :5173)"] -- "HTTPS / JSON<br/>REST API" --> S["Spring Boot server<br/>:443"]
  S -- "JDBC" --> D[("MySQL<br/>Docker container<br/>:3307 → 3306")]
```

- The **browser** loads the React application from the Vite development server and calls the REST API using JSON payloads. During development, Vite proxies the `/api` requests to the backend, so the browser only talks to `http://localhost:5173` (HTTP to Vite, then HTTPS from Vite to the backend).
- The **Spring Boot server** serves HTTPS on port 443, authenticates the requests (see [Security](#security)), handles them, applies the business logic and accesses the database through JDBC (using Spring Data JPA).
- The **MySQL database** runs in a Docker container. The container's port 3306 is published on port 3307 of the host.

#### Docker deployment

**Packaged application.** The whole application is one Docker image (`rubenruiz7/tripmate`) that contains the client and the server: the Spring Boot server and the built React application, which Spring serves as static resources. It runs with Docker Compose next to a standard MySQL container, and the image and the Compose file are published on DockerHub ([`rubenruiz7/tripmate`](https://hub.docker.com/r/rubenruiz7/tripmate) and [`rubenruiz7/tripmate-compose`](https://hub.docker.com/r/rubenruiz7/tripmate-compose)). The user guide is [Execution](execution.md):

```mermaid
flowchart LR
  B["Browser"] -- "HTTPS :443<br/>SPA + REST API" --> A["app container<br/>rubenruiz7/tripmate<br/>Spring Boot :443"]
  A -- "JDBC<br/>(internal network)" --> D[("db container<br/>mysql:9<br/>volume db-data")]
  A -- "SMTP :1025<br/>(internal network)" --> M["mailpit container<br/>axllent/mailpit<br/>test inbox"]
  B -- "HTTP :8025<br/>test inbox" --> M
```

- The **`app` container** serves the SPA and the REST API from the same origin, so the browser needs no proxy. Requests to a client route (for example `https://localhost/trips`, also after a page refresh) return `index.html` so that React Router renders the screen. Unknown `/api/**` URLs keep returning the JSON error and a missing file (for example `/missing.png`) returns 404.
- The **`db` container** is not published on the host: only `app` reaches it, through the Compose network. Its data lives in the named volume `db-data`.
- The **`mailpit` container** is a test mail server: it receives the emails of the `app` container over the Compose network (SMTP, port 1025, not published on the host) and shows them in a web inbox on port 8025, which is published only on `127.0.0.1` (the emails contain the links of the invitations, so no other machine may read them). It keeps nothing after the container is removed. `app` does not wait for it, so the application also starts with another SMTP server (see [Emails](#emails)).

**Image layers.** `docker/Dockerfile` has three stages and the build context is the repository root (`.dockerignore` is an allowlist, so only the sources needed by the build are sent to Docker):

| Stage      | Base image                      | What it does                                                                                      |
| ---------- | ------------------------------- | ------------------------------------------------------------------------------------------------- |
| `frontend` | `node:24-alpine`                | `npm ci` and `npm run build` in `frontend/`                                                       |
| `backend`  | `maven:3.9-eclipse-temurin-21`  | Copies the frontend build into Spring's static resources and packages the jar (`-DskipTests`)     |
| runtime    | `eclipse-temurin:21-jre-alpine` | Only the jar, run by the non-root user `tripmate`; HTTPS on port 443 with the keystore in the jar |

The tests are not run while building the image: they run in CI. The resulting image is about 415 MB (the JRE is 165 MB and the jar 68 MB).

**Compose files.** Both files are self-contained (no `build` section, bind mounts or `env_file`), so they can be published as OCI artifacts. They only differ in the project name and the image tag:

| File                            | Project        | `app` image               | Use                                                    |
| ------------------------------- | -------------- | ------------------------- | ------------------------------------------------------ |
| `docker/docker-compose.yml`     | `tripmate`     | `rubenruiz7/tripmate:0.2` | Released version, downloaded from DockerHub            |
| `docker/docker-compose-dev.yml` | `tripmate-dev` | `rubenruiz7/tripmate:dev` | Image built locally, to test changes before publishing |

The image tag in `docker/docker-compose.yml` is always the `MAJOR.MINOR` tag of the last release (`0.1`, see [Versioning](#versioning)); the release workflow publishes that tag next to the full version. The files published by [continuous delivery](#continuous-delivery) have the tag of each publication instead.

`app` waits for `db` to be healthy (`mysqladmin ping`) before starting. All settings are environment variables with the `${VAR:-default}` syntax, so `docker compose up` works without any configuration:

To change a value, set the variable before the command, for example `SAMPLE_DATA=false docker compose -f docker/docker-compose.yml up -d`.

**Running with Docker Compose.** Requirements: Docker only, and port 443 free on the host (stop the local backend if it is running).

```bash
# Released version
docker compose -f docker/docker-compose.yml up -d

# Local image: build it, tag it as dev and run it
docker build -f docker/Dockerfile -t rubenruiz7/tripmate:dev .
docker compose -f docker/docker-compose-dev.yml up -d
```

The application is then available at https://localhost/ (the browser warns about the self-signed certificate) and the REST API at https://localhost/api/v1/. Log in as `admin@tripmate.com` with the password `admin`, or as one of the [sample users](#sample-data).

**Running from the OCI artifact.** Without cloning the repository, Compose (2.34.0 or later) can run the file published on DockerHub, which is how a user runs the application (see [Execution](execution.md) and [Continuous delivery](#continuous-delivery)):

```bash
docker compose -f oci://docker.io/rubenruiz7/tripmate-compose:latest up -d --yes
```

Before running a file downloaded from a registry, `up` shows its variables and asks "Do you want to proceed with these variables?"; `--yes` answers yes. `down`, `logs` and `ps` do not ask. The tag is `latest` (last release), a release such as `0.1` (or its full version `0.1.0`), or `dev` (last version of `main`); the other commands of the table below work with the same `-f oci://…` instead of the file in `docker/`.

| Goal                                  | Command (use `docker/docker-compose-dev.yml` for the local image)                      |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| Start with the sample users and trips | `docker compose -f docker/docker-compose.yml up -d`                                    |
| Start with an empty database          | `SAMPLE_DATA=false docker compose -f docker/docker-compose.yml up -d`                  |
| See the logs                          | `docker compose -f docker/docker-compose.yml logs -f app`                              |
| Stop, keeping the data                | `docker compose -f docker/docker-compose.yml down` (the next `up` finds the same data) |
| Stop and delete all data              | `docker compose -f docker/docker-compose.yml down -v` (removes the `db-data` volume)   |

`SAMPLE_DATA` is read when the application starts. Uploaded images are stored in the database, so they follow the same rules as the rest of the data: they survive `down` and `up` and disappear with `down -v`. To go from sample data to an empty database, reset the data first with `down -v`.

### Domain model

The persistent entities are `User`, `Trip`, `Activity`, `Participation`, `Invitation`, `ActivityLogEntry` and `Image`. The trip's creator, the activity's author, the two sides of a participation, the trip and the inviter of an invitation, and the trip and the user of a change log line are required. The account of the invited person is optional (an email without an account can be invited), and so are the activity of a log line (it becomes empty when the activity is deleted) and the original of a copied trip. A user participates in a trip at most once (unique trip and user). The three links to an image are optional and each image belongs to at most one entity (`unique` foreign key). Deleting a trip also deletes its participations, invitations, change log, activities and images, and empties `copiedFrom` in its copies, all explicitly in `TripService.delete` (there are no database cascades).

### Server architecture

The backend is organised in three layers (package-by-domain: `user`, `trip`, `activity`, `participation`, `invitation`, `image`, `metrics` and `notification`, plus `common`; each domain with its `controller`, `service` and `repository` subpackages). A controller only calls services and a service is the only one that uses repositories. The diagram shows the dependencies between controllers and services and between services and repositories, without attributes or methods. Services also call each other (for example `TripService` uses `TripAccessService`, `ActivityService` and `ImageService`, and every service that works on a trip asks `TripAccessService` who may do it), and `AuthService` provides the logged-in user; those calls are not drawn to keep it readable. - **Controllers:** receive the HTTP requests under `/api/v1`, validate the input and return the response with its status code; they contain no business logic.
- **Services:** apply the business rules and the owner and role checks, and decide the transactions.
- **Repositories:** Spring Data JPA interfaces that access MySQL; filtering, sorting, pagination and aggregation are done in their queries.
- **Public itineraries (I7–I10).** The public reads are in `PublicTripService` (`PublicTripController`, the only trip endpoints that `SecurityConfig` opens to visitors), which only returns published trips through `TripAccessService.findPublished` (404, never 403). The search of I8 is `TripRepository.searchPublished`, in the query. Publishing is decided by `findForWrite` (creator only) and unpublishing by `findForUnpublish` (creator or administrator, I10). Copying (I9) is `TripService.copyPublic`, in one transaction.
- **Invitations and participants (I1–I3).** The `invitation` package stores the invitations and their answers (`InvitationService`); the creator manages them through `findForWrite`, and the invited person is identified by the email of the logged-in account. Accepting creates a `Participation` (`ParticipationService`, in the `participation` package), and `TripAccessService.findForRead` lets the participants read the trip. Listing and removing participants is in `ParticipantService`, decided by `findForParticipantRemoval`. The emails are sent by the `notification` package (see [Emails](#emails)). **Known limitation:** two identical invitations sent at the same moment can both pass the check for a pending one, because there is no unique constraint for it in the database; the second is an extra pending invitation that the creator can see in the list.
- **Collaborative itinerary (I4).** `TripAccessService.findForItineraryWrite` lets the creator and the participants create, edit and delete any activity of the trip and its picture; the administrator and anyone outside the trip get 403, and `findForWrite` stays creator-only for the trip itself. `ActivityService` records every change in the trip's change log (`ActivityLogService`, entity `ActivityLogEntry`) inside the transaction of the change itself, so a change that fails leaves no line; members read it with `GET /api/v1/trips/{tripId}/activity-log`, ten lines at a time, newest first. Deleting an activity first detaches its log lines (they keep the names), and deleting a trip deletes its log before its activities.
- **Spending charts (I5).** `GET /api/v1/trips/{tripId}/activities/spending` (`ActivityService.findSpending`, read access like `findCost`) gives the data of the two charts of the trip page. The two sums come from `GROUP BY` queries in `ActivityRepository` (`sumCostByCategory`, `sumCostByDay`), which ignore the activities without cost and put those without category in one group; the total is the existing `sumCost`. The service only fills in what a query cannot return: `fillDays` adds the days without cost with 0 and the running sum, so the line covers every day of the trip, and it extends the range to a day outside the trip's dates that has cost (an activity left behind by a change of dates), so the last running sum is always the total. The frontend only draws what it receives. `GET .../activities/cost` is untouched: the small figure of the trip summary does not pay for the two extra queries.
- **Platform metrics (I6).** `MetricsService` (package `metrics`, with no entity or repository of its own) reads three `COUNT`s from the user, trip and activity repositories for `GET /api/v1/admin/metrics`.
- **Known limitation:** two members who edit the same activity at the same time do not warn each other: the last save wins, and both changes appear in the change log. Optimistic locking (a version column on `Activity`, answered with 409 when it is stale) could be added later.

### Client architecture

### Security

Authentication and authorization are implemented with Spring Security.

- **Login:** `POST /api/v1/auth/login` checks the email and password (BCrypt) and returns the user. The response sets a signed JWT (HS256) in the `AuthToken` cookie, which is `HttpOnly` (JavaScript cannot read it), `Secure` (HTTPS only), `SameSite=Strict` and limited to the path `/api`. Because of this, the frontend asks `GET /api/v1/auth/me` to know who is logged in.
- **Every request:** the token is read from the cookie and the user is loaded from the database, so the role always comes from the database (never from the token) and a user blocked or deleted after logging in is rejected immediately. A missing, invalid or expired token is answered with 401 and the cookie is cleared.
- **Roles:** `USER` and `ADMIN`. The URLs under `/api/v1/admin/**` require `ADMIN`; the rest of `/api/**` requires being logged in, except login, logout, registration, reading an image (`GET /api/v1/images/{id}`) and reading the public itineraries (`GET /api/v1/trips/public`, `/api/v1/trips/public/{id}` and `/api/v1/trips/public/{id}/activities`).
- **Administrator:** there is a single administrator, defined in the configuration (`ADMIN_EMAIL`, `ADMIN_NAME` and `ADMIN_PASSWORD_HASH`, a BCrypt hash, never a plain password). On every start-up it is created or updated in the database and any other administrator is demoted to `USER`, so the role cannot be assigned through the API.
- **Blocked users:** a user with status `BLOCKED` cannot log in (403 "Account is blocked"). The blocked check runs after the password check, so someone who does not know the password gets the generic 401 and cannot find out that the account exists.
- **CSRF:** disabled, because the session is stateless and the only credential is a `SameSite=Strict` cookie that browsers do not send on cross-site requests.
- **Errors:** security errors use the same JSON body as the rest of the API: `timestamp`, `status`, `error`, `message` and `path`.
- **Known limitation:** changing the password does not invalidate the sessions already open on other devices. The JWT is stateless and is not tied to the password, so a token issued before the change stays valid until it expires (`JWT_EXPIRATION`, 24 hours by default).
- **Known limitation:** the database schema has no migrations yet; they are planned for version 1.0, with Flyway. Until then the schema is created and extended by Hibernate (`ddl-auto=update`), which cannot add a `NOT NULL` column to a table that already has rows, nor tighten or change existing columns. B4 is the example: trips gained a mandatory creator, so a development database created before B4 must be recreated once (see [Sample data](#sample-data)). The changes of version 0.2 only add tables and columns that are nullable or have a default (`trip.published`, `published_at`, `copied_from_id`, and the participation, invitation and change log tables), so a 0.1 database is extended without losing data (see the CHANGELOG).

### Emails

The server sends one kind of email so far: the invitation to a trip (I1). It is built so that the sending can leave the application later (a separate notification service):

```mermaid
flowchart LR
  S["InvitationService.create<br/>(transaction)"] -- "InvitationCreatedEvent<br/>(plain data)" --> L["InvitationMailListener<br/>after commit, in the background"]
  L --> C["InvitationEmailComposer<br/>mail/invitation.txt"]
  L -- "JavaMailSender" --> M[("SMTP server")]
```

- **After the commit.** `InvitationService` saves the invitation and publishes an `InvitationCreatedEvent`. The listener (`@TransactionalEventListener(AFTER_COMMIT)` plus `@Async`) receives it only once the transaction has committed, so an invitation that is rolled back sends nothing, and a slow or failing SMTP server never delays the response or undoes the invitation.
- **Isolated.** The `notification` package (`config`, `event`, `service`) does not use anything of `trip`, `invitation` or `user`; the only thing it shares with them is the event record, which carries plain data and no entities. Its `toString` shows only the invitation id, so the token and the address cannot reach a log through it.
- **The text.** The subject and the body, in Spanish, are in `src/main/resources/mail/invitation.txt` (first line the subject, then the body, with the placeholders `{inviterName}`, `{tripName}` and `{link}`). `InvitationEmailComposer` fills them in one pass and removes line breaks from the names, so a name cannot add headers. The link is `{APP_PUBLIC_URL}/invitations/{token}`, which opens the invitation page of the application (I2).
- **Configuration.** The SMTP server comes from `spring.mail.*` (environment variables `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SMTP_AUTH`, `MAIL_SMTP_STARTTLS`) and the sender and the public address from `app.mail.from` and `app.mail.public-url` (`MAIL_FROM`, `APP_PUBLIC_URL`). The connection timeouts are five seconds. The tables with the values are in [Docker deployment](#docker-deployment) and in [Execution](execution.md#emails), which also explains how to send real emails with Gmail.
- **Tests.** The composer and the listener have unit tests (the listener also checks that a failure is logged without the token or the address). `InvitationMailIntegrationTest` runs the whole path against a real SMTP server in the tests (GreenMail): the email arrives after the commit with the right link, nothing is sent for a refused or rolled back invitation, and a server that is down does not undo the invitation.
- **Known limitation:** an invitation email that cannot be sent is only logged (the invitation number and the kind of error) and is not retried. The invitation stays pending and appears in the creator's list, but the invited person gets nothing until the creator invites them again, which is not possible while the first invitation is pending. Retrying the sending needs a stored state per email (an outbox) and is left for a later release.

#### Pagination

Every list is paginated in the database query (Spring Data `Pageable`), never in Java. The client sends `?page=0&size=10` (page numbers start at 0; the default size is 10 and the maximum is 50, set with `spring.data.web.pageable.max-page-size`; `?sort=` is accepted and an unknown property is answered with 400). The answer is always a `PageDTO` (`common/dto`):

```json
{ "content": [], "page": 0, "size": 10, "totalElements": 12, "last": false }
```

In the frontend, `usePagedList` (`src/hooks`) loads one page at a time and appends the next one, and `LoadMoreButton` shows "Más resultados" until the server says `last: true`.

#### Images

Images are stored in the database (`Image` entity: a `@Lob` byte array in a MEDIUMBLOB column, the content type and the creation time), as the project requires, and are identified by a random UUID so their URLs cannot be guessed or enumerated.

- **Upload:** `POST /api/v1/images` (logged-in users) takes a multipart form with the picture in the `file` part and answers `201` with a `Location` header and the image data (`id`, `contentType`, `size`). The type must be JPEG, PNG or WebP **and** the first bytes of the file must match the declared type, so a text file renamed to `.png` is rejected with `400`. Images over `IMAGE_MAX_SIZE` get `413`; `spring.servlet.multipart` sets a hard cap of 10 MB above that.
- **Read:** `GET /api/v1/images/{id}` is public so `<img>` tags work without credentials. It answers the bytes with the stored `Content-Type` and `Cache-Control: max-age=31536000, public, immutable`, because an image never changes (a new upload gets a new id).
- **Frontend:** `ImageUpload` uploads the chosen file and `StoredImage` shows an image by id, falling back to `DEFAULT_TRIP_COVER` (`public/Default_trip_image.png`) when there is no id or it fails to load. The avatar of a user is the first image linked to an entity (`User.avatar`, `PUT /api/v1/users/{id}/avatar`): `ImageUpload` takes an `upload` function and `UserAvatar` shows the picture or the initial of the name. Linking images to trips and activities is done by their own features.

#### Errors

Every error has the same JSON body (`ErrorResponse`): `timestamp`, `status`, `error`, `message` and `path`. `GlobalExceptionHandler` maps exceptions to status codes, and the security filters write the same body through `ErrorResponseWriter`.

| Status | When                                                                                                              |
| ------ | ----------------------------------------------------------------------------------------------------------------- |
| 400    | Invalid body (`message` lists `field: problem` sorted by field), malformed JSON, or a parameter of the wrong type |
| 401    | Not logged in, or wrong email or password                                                                         |
| 403    | Access denied (role or ownership), or a blocked account                                                           |
| 404    | `ResourceNotFoundException` (a trip, an image...), or an unknown URL                                              |
| 405    | HTTP method not supported by the URL (the `Allow` header lists the valid ones)                                    |
| 409    | `ConflictException`                                                                                               |
| 500    | Any other exception: logged with its stack trace, but the response only says `Unexpected error`                   |

To report a new error from a service, throw `ResourceNotFoundException` or `ConflictException` with a message that is safe to show.

### Frontend routing and error page

The frontend uses React Router. `src/routes.tsx` lists one route per screen of [the analysis](analysis.md#screens-and-navigation). Every screen of versions 0.1 and 0.2 is built: home, public itineraries (`/public`) and the read-only preview of one (`/public/:tripId`), login, registration, My Trips, trip form, trip detail with the itinerary, activity form, profile, the administrator dashboard `/admin` and its pages `/admin/users` and `/admin/trips`, and the invitation page `/invitations/:token` (I2), which needs a login: a visitor is sent to log in or register and comes back to it. Only the AI generator (`/trips/:tripId/ai-generator`) still shows `PlaceholderPage`, because it belongs to a later version. Every route renders inside `AppLayout` (header, page, footer).

- **Unknown URLs** match the `*` route and show `ErrorPage` with the 404 message.
- **Failures while loading data**: services use `request()` (`src/services/apiError.ts`), which throws `ApiError` (non-2xx answer, with the status) or `NetworkError` (no answer). A component that cannot load its data rethrows the error and the route's `errorElement` shows `ErrorPage` inside the same layout, with a message for 404, 5xx or no connection and a button back to the home page.
- **Texts**: Spanish UI texts are written in the component that shows them, as in the rest of the frontend.

**Profile (B3).** A registered user reads and edits their own profile at `/api/v1/users/{id}`: only that user can (another user's id is a 403, a missing one a 404). The token identifies the user by id, not by email, so changing the email does not log the user out and no token refers to the old address. The new email follows the registration rules (lower case, 409 for a taken one or the administrator's). The password change is `PUT /api/v1/users/{id}/password`: it requires the current password (a wrong one is a 400, because 401 means "log in again" for the application and 403 means "not allowed on this profile") and the new one follows the 8–72 character rule. The avatar is an `Image` linked to the user (`PUT`, `GET` and `DELETE /api/v1/users/{id}/avatar`), validated by `ImageService` like any other image; replacing or deleting it deletes the previous image. The administrator can only change their avatar. Responses never contain the password hash.

**Trips (B4).** A registered user creates, reads, edits and deletes their own trips at `/api/v1/trips`. Every trip has a creator; only the creator can change it (since version 0.2 its participants also read it, I2), and the cover (`/api/v1/trips/{id}/cover`) follows the same rule (another user's trip is a 403, a missing one a 404, and 404 is checked before 403, so a missing trip is reported as missing to anyone). The administrator is a user like any other for their own trips; on other users' trips they can only read and delete (trip moderation, B8), never edit. The body is validated before the service runs (400): `name` and `destination` are required (up to 100 characters), the dates are required and the end must not be before the start (the same day is a one-day trip), `budget` is optional (up to 2 decimals, not negative) and `description` optional (up to 2000 characters). `GET /api/v1/trips` returns only the trips of the logged-in user, paginated and sorted in the query; `sort` accepts only `id`, `name`, `destination`, `startDate`, `endDate` and `createdAt`. The cover is an `Image` linked to the trip, validated like any other image; a trip without cover has `coverImageId: null` and the application shows its default image (the API answers 404 to `GET /cover`). Replacing or deleting a cover, and deleting a trip, delete the image they stop using.

**Itinerary (B5).** The creator of a trip (since version 0.2 also its participants, I4) creates, reads, edits and deletes its activities at `/api/v1/trips/{tripId}/activities`, with an optional image, and browses the itinerary one day at a time on the trip page. **Public home page (B1) and public itineraries (I7).** Anyone, logged in or not, sees the home page at `/` with a carousel of the public itineraries, and opens one at `/public/:tripId` to browse its itinerary day by day without being able to change anything. A public itinerary is a trip whose creator published it: `Trip.published` (false by default) and `Trip.publishedAt`, which orders the list, newest first. The creator publishes or unpublishes it with `PUT /api/v1/trips/{id}/publication` (the B7 status pattern: a sub-resource with a value, idempotent), through `TripAccessService.findForWrite`, so only the creator may publish, not even the administrator. Unpublishing goes through `TripAccessService.findForUnpublish` (creator or administrator), so the administrator can remove any itinerary from the public list while the trip stays with its creator (moderation, I10); the frontend shows "Despublicar" to the administrator on `/public` and `/public/:tripId`. `Trip.publish` keeps the first publication date and cuts it to microseconds, which is what the database stores, so the date answered when publishing is the one every later read gives. Hibernate adds the two columns to an existing database (`published` is filled with false), so existing trips start unpublished. The carousel reads three public, read-only endpoints under `/api/v1/trips/public`, added to `SecurityConfig` as exact `GET` paths (every other trip endpoint still needs a login). `TripAccessService.findPublished` answers 404, never 403, for a trip that is not published. `PublicTripDTO` is a whitelist: the author's name, never an email, an id of the author or participants. The home page shows three itineraries at a time (`?size=3`) and stops after the third page, so it shows the nine most recently published; each has the first activity of its first three days, which `ActivityRepository.findFirstOfFirstDays` reads for the whole page in one query. The "Ver todos" link goes to `/public`, the public itineraries page (I8). The sample data publishes five trips of three authors (the administrator's three, one of Ana and one of Carlos) only when it creates them, so a trip somebody unpublished stays unpublished after a restart; an existing development database gets them after a reset.

**Copying a public itinerary (I9).** A logged-in user copies a public itinerary into a new trip of their own with `POST /api/v1/trips/public/{id}/copies`, which answers 201 with the new trip and its URL in `Location`. It is the only non-GET URL under `/api/v1/trips/public`, and `SecurityConfig` still lists only the three GET paths as public, so a visitor gets 401. `TripService.copyPublic` finds the trip with `TripAccessService.findPublished` (404, never 403, for a trip that is not published) and does everything in one transaction: the new `Trip` (same name, destination, budget and description, not published, `copiedFrom` pointing at the original), its cover, and its activities through `ActivityService.copyAll`, with the user as author. Every picture goes through `ImageService.copy`, which stores a new `Image` row with the same bytes and type, so the copy never shares a row with the original. The optional body has a `startDate`: the offset is the number of days between the original start date and it, applied to the trip's two dates and to every activity, so the length and the day of each activity are kept (without it the offset is 0). `Trip.copiedFrom` is a lazy self reference (`copied_from_id`); `TripDTO.copiedFromId` reads its id without loading the original. There is no database cascade: `TripService.delete` first deletes the activities, then runs `TripRepository.clearCopiedFrom` (an update that sets `copied_from_id` to null on the copies) and then deletes the trip, so a copy outlives its original. In the application, the preview page `/public/:tripId` has the "Copiar en tu cuenta" button: a visitor is sent to `/login` with the page in the router state (the same mechanism `RequireAuth` uses), so after logging in they come back to the preview; a logged-in user fills the optional date in `CopyTripModal` and lands on `/trips/{newId}`, whose page shows the message left in the router state.

**Public itineraries page (I8) and moderation (I10).** `/public` lists every public itinerary, newest publication first, ten at a time with "Más resultados", with a search by trip name or destination and empty states for no public trips and for a search without results; "Viajes públicos" in the header opens it for everyone. `GET /api/v1/trips/public?search=` keeps the published trips whose name or destination contains the text, ignoring case and the spaces around it, in the query (`TripRepository.searchPublished`); a blank search lists everything. To moderate, the administrator uses the same `PUT /api/v1/trips/{id}/publication` with `{"published": false}`: `TripAccessService.findForUnpublish` accepts the creator or the administrator (404 before 403), while publishing keeps `findForWrite`, so the administrator never publishes another user's trip. The trip leaves the list and the carousel, and its creator keeps it, unpublished, in "Mis viajes". The administrator sees "Despublicar", with a confirmation (`UnpublishTripModal`), on every line of `/public` and on the preview; after it the list reloads, or the preview goes back to `/public`, with a notice.

**User management (B7).** The administrator lists, searches, edits and blocks users at `/api/v1/admin/users`, and uses the `/admin/users` page (link "Usuarios" in the header, only for the administrator). The URLs are under `/api/v1/admin/**`, which `SecurityConfig` already restricts to the `ADMIN` role, so a regular user gets 403 and an anonymous visitor 401 without any check in the service, and `/api/v1/users/{id}` keeps meaning "one's own profile". The list shows regular users only (never the administrator) and is paginated; `search` is trimmed and matches the name or the email ignoring case inside the query, and `sort` accepts only `id`, `name`, `email` and `registrationDate` (400 otherwise; sorted by name by default). Editing uses the same body, validation, lower-casing and 409 rules as registration and the profile. Blocking is `PUT /api/v1/admin/users/{id}/status` with `{"status": "BLOCKED"}` (or `ACTIVE`), idempotent. The administrator's own account cannot be edited or blocked: the request is well formed, so it is a 403 (the same answer as when the administrator edits their own profile in B3), not a 400, and its details come from the configuration anyway. Checks run in this order: 404, 403, then the body rules (409). A blocked user cannot log in (403 "Account is blocked") and their open session stops working on the next request, because `ActiveUserJwtConverter` reloads the user on every request (the API answers 401 and clears the cookie, so the SPA sends them to log in again); unblocking makes the same token valid again until it expires. On the frontend, `RequireAdmin` guards `/admin*` inside `RequireAuth` and gives anyone else the 403 error page; editing is a modal on the list and blocking asks for confirmation with `ConfirmModal`.

**Trip moderation (B8).** The administrator lists and searches every trip at `GET /api/v1/admin/trips` (under `/api/v1/admin/**`, so a regular user gets 403 and an anonymous visitor 401 from `SecurityConfig`), reviews any trip and deletes it. **Answering invitations (I2).** The invited person lists the pending invitations addressed to their email with `GET /api/v1/invitations`, opens the one the email link points at with `GET /api/v1/invitations/token/{token}` and answers it with `PUT /api/v1/invitations/{id}/status`. Only the logged-in user whose normalised email equals the invited email may see or answer an invitation (403 for anyone else, the creator and the administrator included; 401 for a visitor); the matching is by email and not by the account saved when it was created, because the person may have registered later or changed their email. An invitation is answered once (409), a deleted trip deletes its invitations (404), and accepting creates the `Participation` and saves the account on the invitation in one transaction. **Invitations do not expire**: the token alone gives nothing, because only the addressee's account can use it, so a link that leaks is useless to anyone else, and an expiry would add a column, a setting and one more error without a requirement for it. The answers never include the email, the token or user ids. Participants read the trip through `TripAccessService.findForRead`; writing, publishing, inviting and deleting stay with the creator (I3 adds managing the participants). `GET /api/v1/trips` lists the trips the user created or joined with one query that pages and sorts in the database.

**Managing participants (I3).** `GET /api/v1/trips/{tripId}/participants` lists the people who joined a trip and `DELETE /api/v1/trips/{tripId}/participants/{userId}` removes one of them or lets a participant leave. Everyone who can read the trip (its creator, its participants and the administrator) may list them, because the trip page shows who is going; each entry has the user id, the name, the avatar id (a UUID, null without picture) and the join date, and **the email only reaches the trip's creator** (it is null for everyone else). The creator is not a row, because they have no participation. The creator removes any participant; a participant can only remove themselves, which is leaving. Anyone else gets 403 (another participant, the administrator, a stranger, or a user who was already removed), an unknown trip or a user who is not a participant is 404, and the creator "leaving" their own trip is a 409 whose message says to delete the trip instead. The checks run in the order 404, 403, 409, 404 and the first two are decided by `TripAccessService.findForParticipantRemoval`; `ParticipantService` holds the operations, in its own class because `TripAccessService` already depends on `ParticipationService`. The change is immediate, because reading a trip checks the participation on every request: the removed user's next request to the trip is a 403 and the trip leaves their "My trips". Only the participation is deleted: the invitation stays `ACCEPTED` as history and the person can be invited again, because I1 only refuses a second invitation while one is pending. The list is one query that projects straight into the DTO, with the paging and the sorting done in the database. Every `TripDTO` also carries `participantCount`, the number of people who joined the trip without counting its creator, so that the number of the card in "My trips" is the number of rows of the participants list: for a page of trips it comes from one grouped query over the ids of the page (`ParticipationRepository.countByTripIds`), and for a single trip from a plain count. **Note for I4:** once activities have authors, removing or leaving has to decide what happens to the activities of that user before the participation is deleted; the proposal is that they stay in the trip, because the itinerary is shared and the creator can edit or delete any of them.

**Collaborative itinerary and change log (I4).** The creator and the participants create, edit and delete any activity of the trip, and its picture, with the same endpoints as B5; the rule is `TripAccessService.findForItineraryWrite` (creator or participant), so the administrator and anyone outside the trip still get 403, and editing the trip itself stays creator-only. Each of those changes writes **one** line of the trip's change log in the same transaction, through `ActivityLogService` (its methods require an existing transaction, so a line can never be written without its change, and a change that fails leaves none): `CREATED`, `UPDATED` or `DELETED`, with the trip, the activity, the user and the time. An edit lists in `changedFields` the names of the fields that really changed (`ActivityFieldChanges` compares the stored form of each value, so `16.5` and `16.50` or padded text are not changes), never their values; a change of the picture is an edit of `image`; an edit that changes nothing still writes its line, with no fields, and removing a picture that is not there writes nothing. The activity name and the user name are copied into the line, and when an activity is deleted its lines are first detached (`activity_id` becomes null) and the `DELETED` line is written last, so the log keeps reading the same. `GET /api/v1/trips/{tripId}/activity-log` lists the log, newest first and ten at a time (`sort` accepts `id` and `createdAt`, another property is a 400), for anyone who can read the trip; deleting the trip deletes its log before its activities, and removing a participant keeps their activities and their lines. `ActivityDTO` has `authorName`, read in the same query as the activities (a join fetch, not one query per card); the public itinerary returns it as null, so it never names the members. The trip page shows "Historial de cambios" below the itinerary: the 5 latest lines, "Ver más" for 10 more (asking the server for the next page when needed) and "Ver menos" to go back to 5, and it is read again after an activity is deleted there.

## Development process

The project follows an iterative and incremental process based on the principles of the [Agile Manifesto](https://agilemanifesto.org/): the software is built in phases that each end with a working release (0.1, 0.2 and 1.0), the plan is adjusted as the work advances, working software is preferred to extensive documentation, and every feature is demonstrated with its tests before it is merged. It is not Scrum: there are no sprints, roles or ceremonies. It takes some practices from two methods:

- **Extreme Programming (XP):**
  - _Continuous integration_: every push runs the build, the code style checks, the unit tests and the static analysis, and every pull request runs the whole test suite (see [Continuous integration](#continuous-integration)).
  - _Automated tests_: every feature is only done when it has its six types of tests (see [Types of tests](#types-of-tests)).
  - _Small releases_: a release at the end of every phase, and every feature in a short branch merged by a small pull request.
  - _Refactoring_: the code is reorganized when a feature needs it, for example when the access rule for trips moved to `TripAccessService` so that later features extend it in one place.
- **Kanban:** the tasks are cards on a visual board, they flow through its columns, and the work in progress is limited (see [Task management](#task-management)).

### Task management

Tasks are managed as GitHub Issues and organized on a Kanban board in [GitHub Projects](https://github.com/orgs/codeurjc-students/projects/46). Each phase is broken down into issues that move through the board columns as they progress, and the number of tasks in progress at the same time is limited. A task is only considered done when its automated tests are implemented and the quality controls pass.

### Git

The code is stored in a Git repository hosted on GitHub. The branching strategy is **GitHub Flow**:

- `main` is the stable branch. It never receives direct commits, and its code is always ready to be deployed.
- Each feature or fix is developed in its own short-lived branch, named `feature/<ID>-<short-description>` (for example, `feature/B4-trip-crud`) or `feature/<short-description>` for technical work, `fix/<short-description>`, `refactor/...` or `docs/...`. A branch is deleted after its pull request is merged.
- Branches are merged into `main` through pull requests, which can only be merged when the full quality workflow passes. Each pull request closes its related issues.

### Continuous delivery

Four more GitHub Actions workflows publish the application on DockerHub. They only add files: the quality workflows above are not modified, and nothing is published by them.

| Workflow                                    | Trigger                                         | Image `rubenruiz7/tripmate` and artifact `rubenruiz7/tripmate-compose` tags    | Compose file published          |
| ------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------ | ------------------------------- |
| **Deliver dev** (`deliver-dev.yml`)         | Every push to `main`                            | `dev`                                                                          | `docker/docker-compose-dev.yml` |
| **Deliver release** (`deliver-release.yml`) | A GitHub release is published                   | `x.y.0`, `x.y` and `latest` (a pre-release does not move `latest`)             | `docker/docker-compose.yml`     |
| **Deliver manual** (`deliver-manual.yml`)   | Manually (_Actions → Run workflow_), any branch | `<branch>-<YYYYMMDD>-<short commit>`, for example `feature-x-20261023-abc1234` | `docker/docker-compose-dev.yml` |
| **Publish Docker** (`publish-docker.yml`)   | Called by the three above (`workflow_call`)     | The tag it receives, plus optional aliases                                     | The file it receives            |

`publish-docker.yml` does the work, always in the same way: it logs in to DockerHub, builds `docker/Dockerfile` and pushes the image, and publishes the Compose file as an OCI artifact (`docker compose publish`). The credentials are the repository secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` (a DockerHub access token with read and write permission); they are only used by the login step and never printed.

**Which image the artifact runs.** The committed Compose files are never edited. The workflow copies the file to a temporary folder and changes only its `app` image line to `rubenruiz7/tripmate:<tag>`; everything else, including the `${VAR:-default}` expressions, stays as it is, so the artifact is as configurable as the original. It stops if more than one line changed and checks the result with `docker compose config --images`. After publishing, it reads every artifact back from DockerHub and checks the image again. The image inside an artifact is always an immutable tag (`dev`, the version, or the branch-date-commit tag): `rubenruiz7/tripmate-compose:latest` and `:0.1` run `rubenruiz7/tripmate:0.1.0`, not `latest`, so an artifact keeps running the same image. The committed file names `rubenruiz7/tripmate:0.1`, which is why that tag is published too; the published copy replaces it with `0.1.0`.

| Case         | Artifact tags            | Image run by the artifact                                   |
| ------------ | ------------------------ | ----------------------------------------------------------- |
| Push to main | `dev`                    | `rubenruiz7/tripmate:dev`                                   |
| Release 0.2  | `0.2.0`, `0.2`, `latest` | `rubenruiz7/tripmate:0.2.0`                                 |
| Manual run   | The branch tag           | `rubenruiz7/tripmate:feature-x-20261023-abc1234` (same tag) |

**Docker Compose version.** `docker compose publish` and `-f oci://…` need Compose 2.34.0 or later (before that, `publish` was an alpha command). The runner image can change its Compose version without notice, so the workflow installs a pinned version with `docker/setup-compose-action` (`COMPOSE_VERSION` in `publish-docker.yml`) and fails if the installed version is different. Every `docker compose` command that talks to the registry runs with its input closed, `--yes` where Compose supports it, and a step timeout, so it cannot wait for a confirmation.

**Manual tags.** Docker tags cannot contain `/` and are limited to 128 characters, so the branch name is converted to lower case, every character outside `a-z 0-9 _ . -` becomes `-` (`feature/x` becomes `feature-x`) and it is shortened if needed; the date is UTC.

**Release gate.** The release workflow does not repeat the tests. Before publishing it checks that the release tag is `MAJOR.MINOR` (for example `0.1`; a `v` prefix or a third number is rejected), that the tagged commit is on `main`, and that the Basic quality run of that commit has succeeded; if that run is still in progress it waits for it (up to 15 minutes), and it fails if it did not succeed. This is enough because of the branch protection rules of `main`: **the gate assumes that `main` only receives pull requests with the full quality workflow passing** (_Require a pull request_ and required status checks), so a commit on `main` has already passed the whole test suite. If the protection is removed, the gate no longer guarantees it. The dev workflow and the manual workflow do not check anything: they publish development images.

**Where to see the result.** The summary of each run lists the published image and artifact, and the DockerHub repositories [`rubenruiz7/tripmate`](https://hub.docker.com/r/rubenruiz7/tripmate) and [`rubenruiz7/tripmate-compose`](https://hub.docker.com/r/rubenruiz7/tripmate-compose) show the tags. To try a branch before merging, run _Deliver manual_ on it and use the tag printed in the summary: `docker compose -f oci://docker.io/rubenruiz7/tripmate-compose:<tag> up -d --yes`.

### Versioning

TripMate follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html): `MAJOR.MINOR.PATCH`. While the major version is `0`, the minor version changes with each release that adds functionality (`0.1.0` with features B1–B8, `0.2.0` with I1–I10) and the patch version with fixes. A release is named with two numbers, `MAJOR.MINOR` (`0.1`, no `v` prefix), and its version is `MAJOR.MINOR.0` (`0.1.0`): the Git tag and the GitHub release are `0.1`, the files and the image use `0.1.0`, and the image and the Compose artifact are also published as `0.1` so that the committed Compose file resolves. The release workflow rejects any other tag.

| Place                         | Value                                                   |
| ----------------------------- | ------------------------------------------------------- |
| Git tag and GitHub release    | `x.y`                                                   |
| `backend/pom.xml`             | `x.y.0` in a release, `x.y+1.0-SNAPSHOT` after it       |
| `frontend/package.json`       | `x.y.0` in a release, `x.y+1.0` after it                |
| `rubenruiz7/tripmate`         | `x.y.0`, `x.y` and `latest`                             |
| `rubenruiz7/tripmate-compose` | `x.y.0`, `x.y` and `latest` (all run the image `x.y.0`) |
| `docker/docker-compose.yml`   | Image `rubenruiz7/tripmate:x.y`                         |
| `CHANGELOG.md`                | A section `## [x.y.0] - date`                           |
| `main` (after the first push) | Image and Compose artifact `dev`                        |

**Releasing a version `x.y`** (for example `0.1`, whose version is `0.1.0`):

1. Check that `main` is green (CI and SonarQube Cloud quality gate) and create a branch `release/x.y`.
2. Set the version `x.y.0` in `backend/pom.xml` and `frontend/package.json` (with its lockfile).
3. Set the `x.y` tag in `docker/docker-compose.yml` (`rubenruiz7/tripmate:x.y`).

### Running the application

This section runs the application from the source code. To run the packaged application with Docker only, see [Docker deployment](#docker-deployment).

**Requirements:** Java 21, Node.js (LTS version) and Docker ([Docker Desktop](https://docs.docker.com/desktop/) on Windows and Mac).

1. **Start the database.** The first time, create the MySQL container (the values must match `backend/src/main/resources/application.properties`):

   ```bash
   docker run -d --name tripmate-mysql -e MYSQL_ROOT_PASSWORD=password -e MYSQL_DATABASE=tripmate -p 3307:3306 mysql:9
   ```

   The next times, start the existing container:

   ```bash
   docker start tripmate-mysql
   ```

   The backend reads its database settings from environment variables, with defaults for the local container:

   | Variable      | Default                                |
   | ------------- | -------------------------------------- |
   | `DB_URL`      | `jdbc:mysql://localhost:3307/tripmate` |
   | `DB_USERNAME` | `root`                                 |
   | `DB_PASSWORD` | `password`                             |
   | `DDL_AUTO`    | `update`                               |

   Tests use `create-drop` through `backend/src/test/resources/application.properties`.

2. **Start the test inbox** (optional: only to see the invitation emails). Mailpit catches the emails that the backend sends, so nothing reaches a real address. The first time:

   ```bash
   docker run -d --name tripmate-mailpit -p 1025:1025 -p 8025:8025 axllent/mailpit:v1.33.1
   ```

   The next times, `docker start tripmate-mailpit`. The emails are read at http://localhost:8025. The backend sends to `localhost:1025` by default, so nothing else has to be configured, except the address of the links: they start with `APP_PUBLIC_URL` (`https://localhost` by default), and the backend alone does not serve the web client, so start it with `APP_PUBLIC_URL=http://localhost:5173`, the address of the Vite server (step 5). The other variables are in [Execution](execution.md#email-settings). Without the inbox the invitations still work: the email fails, is logged, and nothing else changes. On Docker Desktop for Windows the SMTP port published on the host did not answer on the development machine (see [Problems and solutions](#problems-and-solutions)); if the emails do not arrive, run the application with Docker Compose instead.

3. **Check the security configuration.** The backend serves HTTPS on port 443 with a self-signed development certificate that is already in the repository (`backend/src/main/resources/keystore.p12`, password `password`, only for development). It also reads the administrator and the token settings from environment variables, with development defaults:

   | Variable                | Default                                       | Description                                                                                                                                  |
   | ----------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
   | `SERVER_PORT`           | `443`                                         | HTTPS port of the backend                                                                                                                    |
   | `SSL_KEYSTORE`          | `classpath:keystore.p12`                      | PKCS12 keystore with the certificate (`file:/path/to/keystore.p12` for an external one)                                                      |
   | `SSL_KEYSTORE_PASSWORD` | `password`                                    | Keystore password                                                                                                                            |
   | `ADMIN_EMAIL`           | `admin@tripmate.com`                          | Email of the only administrator                                                                                                              |
   | `ADMIN_NAME`            | `Administrator`                               | Name of the administrator                                                                                                                    |
   | `ADMIN_PASSWORD_HASH`   | BCrypt hash of the password `admin`           | BCrypt hash of the administrator password. The application does not start with anything else                                                 |
   | `JWT_SECRET`            | development key (in `application.properties`) | Base64 key used to sign the tokens, at least 32 bytes                                                                                        |
   | `JWT_EXPIRATION`        | `PT24H`                                       | Lifetime of the login cookie and token (ISO-8601 duration)                                                                                   |
   | `SAMPLE_DATA`           | `true`                                        | Loads the sample users, their trips and the administrator's trips (five of them published) that are missing at start-up (`false` to disable) |
   | `SAMPLE_USERS_PASSWORD` | `Demo-2026`                                   | Password of the sample users, encoded when they are created (development only)                                                               |
   | `IMAGE_MAX_SIZE`        | `5MB`                                         | Largest image accepted by `POST /api/v1/images`                                                                                              |

   **In production, `ADMIN_PASSWORD_HASH`, `JWT_SECRET` and the keystore must be replaced** with private values. To create a hash for the administrator password (the `$` characters must not be expanded by the shell, so use single quotes):

   ```bash
   docker run --rm httpd:2 htpasswd -bnBC 10 "" 'my-admin-password' | tr -d ':\n'
   export ADMIN_PASSWORD_HASH='<the hash printed above>'
   ```

   To generate a new `JWT_SECRET`: `openssl rand -base64 32`.

   The development keystore was generated with the following command (run inside `backend/`); it is only needed to replace it, for example if it expires (validity: 10 years):

   ```bash
   keytool -genkeypair -alias tripmate -keyalg RSA -keysize 2048 -validity 3650 \
     -storetype PKCS12 -keystore src/main/resources/keystore.p12 -storepass password \
     -dname "CN=localhost, OU=TripMate, O=URJC, C=ES" -ext "SAN=dns:localhost,ip:127.0.0.1"
   ```

   The certificate is self-signed, so browsers and tools warn about it when they connect to the backend directly (for example `curl` needs `-k`). The frontend does not show the warning because Vite proxies the requests.

4. **Start the backend** (it loads the sample data and creates the administrator on start-up):

   ```bash
   cd backend
   ./mvnw spring-boot:run        # Windows: .\mvnw.cmd spring-boot:run
   ```

   On Linux a normal user cannot use ports below 1024: run the backend on another port (`SERVER_PORT=8443 ./mvnw spring-boot:run`) and give the same address to the frontend with `BACKEND_URL=https://localhost:8443`. The CI workflow does the same.

5. **Start the frontend** in another terminal:

   ```bash
   cd frontend
   npm install                   # only the first time or when dependencies change
   npm run dev
   ```

   The Vite proxy sends `/api` to `https://localhost` and accepts its self-signed certificate. If the backend uses another address, set `BACKEND_URL` before `npm run dev` (for example `BACKEND_URL=https://localhost:8443`).

6. **Open the application** at http://localhost:5173

| Service                      | URL                               |
| ---------------------------- | --------------------------------- |
| Web application              | http://localhost:5173             |
| REST API                     | https://localhost/api/v1/         |
| Swagger UI                   | https://localhost/swagger-ui.html |
| Test inbox (Mailpit, step 2) | http://localhost:8025             |

With the default configuration, you can log in as the administrator with `admin@tripmate.com` and the password `admin`. Quick check with `curl`:

```bash
curl -k -i -X POST https://localhost/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"admin@tripmate.com","password":"admin"}'
```

To stop everything, press `Ctrl + C` in the backend and frontend terminals and run `docker stop tripmate-mysql` (and `docker stop tripmate-mailpit` if you started the test inbox).

The administrator also gets three trips, written in Spanish like the rest of what the home page shows: "Roma en cinco días", "Escapada a las Maldivas" and "Lo mejor de Tokio", with a budget, a description, a cover photo and activities on every day of the trip (12, 14 and 14 activities). **Public itineraries in the sample data (I7).** Five trips of three authors are published: the administrator's three, Ana's "Lisbon getaway" and Carlos's "Andalusia route" (the home page carousel shows them newest first, Roma first). **Upgrading a development database from before B4.** Trips now have a mandatory creator, and Hibernate cannot add that column to a table that already has rows, so recreate the database once: `docker rm -f tripmate-mysql` and the `docker run` command of [Running the application](#running-the-application) again (or `docker compose -f docker/docker-compose.yml down -v` for the Compose database). Tests and CI always start from an empty database.

## Design decisions

Relevant technical decisions taken during the development, with their reasons.

| Date     | Decision                                                                                                                                                                                                                                                                          | Alternatives considered                                                                                                          | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Sep 2026 | Telegram as the instant messaging platform                                                                                                                                                                                                                                        | WhatsApp                                                                                                                         | The Telegram Bot API is free and allows bots to manage groups (invite links, join request approval, removing members), which the trip group feature needs                                                                                                                                                                                                                                                                                                                                                                            |
| Sep 2026 | Modular monolith organized by domain                                                                                                                                                                                                                                              | Classic layered monolith                                                                                                         | Makes it easier to split the application into independent services in TFG2                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Oct 2026 | Testcontainers with MySQL for integration and system tests                                                                                                                                                                                                                        | In-memory H2 database                                                                                                            | Tests run against the same database engine used in production, avoiding SQL dialect differences                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Oct 2026 | Code style checks in CI (Spotless, ESLint, Prettier)                                                                                                                                                                                                                              | Only formatting on save                                                                                                          | Guarantees a consistent style regardless of the editor and makes style errors visible in every push                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Oct 2026 | `.gitattributes` forcing LF line endings                                                                                                                                                                                                                                          | Relying on each machine's Git configuration                                                                                      | The project is developed on Windows and CI runs on Linux; the checks must behave the same in both                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Oct 2026 | MySQL container published on host port 3307                                                                                                                                                                                                                                       | Default port 3306                                                                                                                | Avoids conflicts with a local MySQL installation using port 3306                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Oct 2026 | JWT in an `HttpOnly` cookie, validated with Spring Security's own resource server (Nimbus)                                                                                                                                                                                        | Token in `localStorage` sent as a `Bearer` header; a JWT library such as jjwt                                                    | JavaScript cannot read the cookie, which limits the damage of an XSS attack; no extra dependency is needed                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Oct 2026 | CSRF protection disabled in Spring Security (stateless API)                                                                                                                                                                                                                       | CSRF tokens (`CookieCsrfTokenRepository`)                                                                                        | The API has no server session or form login; its only credential is the `AuthToken` cookie (`HttpOnly; Secure; SameSite=Strict`), which browsers never send on cross-site requests. Tokens would add a header to every mutation without closing a real gap                                                                                                                                                                                                                                                                           |
| Oct 2026 | The user is loaded from the database on every authenticated request                                                                                                                                                                                                               | Trusting the role stored in the token until it expires                                                                           | A blocked user is rejected immediately and the role cannot become stale; the cost is one query by primary key per request                                                                                                                                                                                                                                                                                                                                                                                                            |
| Oct 2026 | The administrator is defined in the configuration and synchronized into the `users` table on start-up                                                                                                                                                                             | Keeping the administrator only in memory                                                                                         | Other entities (for example the sample trips created by the administrator) can reference it, and it still cannot be created or assigned through the API                                                                                                                                                                                                                                                                                                                                                                              |
| Oct 2026 | HTTPS on port 443 by default, with a self-signed development keystore committed to the repository                                                                                                                                                                                 | HTTP in development and HTTPS only in production                                                                                 | Development behaves like production (`Secure` cookie) and CI needs no extra setup; the keystore holds nothing private of the real deployment                                                                                                                                                                                                                                                                                                                                                                                         |
| Oct 2026 | CI runs the backend on HTTPS port 8443 (`SERVER_PORT`)                                                                                                                                                                                                                            | Port 443                                                                                                                         | The GitHub Actions runner cannot bind ports below 1024                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Oct 2026 | One Docker image with the Spring Boot server serving the built React application                                                                                                                                                                                                  | A separate frontend container (for example nginx)                                                                                | The SPA and the API share the same origin (no CORS or proxy), there is one HTTPS endpoint and a single artifact to publish, as the guide asks                                                                                                                                                                                                                                                                                                                                                                                        |
| Oct 2026 | The container listens on port 443 as the non-root user `tripmate`, with `sysctls: net.ipv4.ip_unprivileged_port_start: 0` in the Compose files                                                                                                                                    | The container on 8443 published as `443:8443`; running the container as root                                                     | The guide asks for HTTPS on port 443. The sysctl lets a non-root process bind port 443 inside the container's own network namespace, so the process does not run as root; it was verified on Docker Desktop. If a platform rejects the sysctl, the fallback is to run the container as root                                                                                                                                                                                                                                          |
| Oct 2026 | Two Compose files (release and `dev`) with different project names                                                                                                                                                                                                                | One file with the image tag as a variable                                                                                        | The guide asks for a released and a development file, each publishable as an OCI artifact; different project names keep their volumes and containers separate                                                                                                                                                                                                                                                                                                                                                                        |
| Oct 2026 | The published Compose file is a copy of the committed one with only the `app` image line changed (`sed`)                                                                                                                                                                          | Writing it with `docker compose config`; `yq`; one file with the tag as a variable                                               | `config` resolves every variable to its default and `yq` removes blank lines; changing one line keeps the file identical to the committed one and as configurable, and the result is checked with `config --images`                                                                                                                                                                                                                                                                                                                  |
| Oct 2026 | A Compose artifact always points to an immutable image tag (`x.y.z`, `dev` or the branch tag), also the artifact tagged `latest`                                                                                                                                                  | An artifact `latest` that runs the image `latest`                                                                                | An artifact then keeps running the same image, and the version of the application it runs is always known                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Oct 2026 | Docker Compose pinned in the delivery workflow (`docker/setup-compose-action`)                                                                                                                                                                                                    | The version installed in the runner image                                                                                        | `publish` needs Compose 2.34.0 or later and the runner image changes its version without notice                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Oct 2026 | The release workflow checks that the commit is on `main` and that Basic quality passed (waiting up to 15 minutes), instead of running the tests again                                                                                                                             | Re-running every test; no check                                                                                                  | The tests already ran in the pull request (branch protection on `main`) and the full workflow cannot be reused; the check also covers a release created on a commit whose analysis is still running                                                                                                                                                                                                                                                                                                                                  |
| Oct 2026 | Releases publish `x.y.z` and `latest`, never `x.y`                                                                                                                                                                                                                                | Also a moving `x.y` tag                                                                                                          | One exact tag per release and no tag that changes under the user; the Compose file of the release names the full version                                                                                                                                                                                                                                                                                                                                                                                                             |
| Nov 2026 | Releases are tagged `MAJOR.MINOR` (`0.1`) and publish `x.y.0`, `x.y` and `latest`; the committed Compose file names `rubenruiz7/tripmate:x.y` (replaces "never `x.y`" above)                                                                                                      | Tag `x.y.z` with only `x.y.z` and `latest`                                                                                       | The TFG guide asks for releases named `0.1` and a Compose file that resolves `rubenruiz7/tripmate:0.1`. The artifact still runs the immutable `x.y.0`, so it never changes under the user                                                                                                                                                                                                                                                                                                                                            |
| Oct 2026 | `.dockerignore` as an allowlist                                                                                                                                                                                                                                                   | A list of excluded folders                                                                                                       | Nothing enters the build context unless the build needs it, so private files, `.git` and documentation cannot end up in an image                                                                                                                                                                                                                                                                                                                                                                                                     |
| Oct 2026 | The administrator's own profile is read-only except the avatar (changing its name, email or password answers 403)                                                                                                                                                                 | Letting the administrator edit its profile like any other user                                                                   | The administrator's name, email and password hash come from the configuration and are written to the database on every start-up: a name or password changed through the API would be lost on the next restart, and a changed email would make the next start-up create a second administrator account with the configured email and demote the edited one. The avatar is not in the configuration, so it can be changed                                                                                                              |
| Oct 2026 | Avatars are shown through the public `GET /api/v1/images/{id}` (the `avatarId` of the user), while `GET /api/v1/users/{id}/avatar` requires login                                                                                                                                 | Serving avatars only from the user URL; making the user URL public                                                               | The image URL is a random UUID that cannot be guessed or enumerated (the same as the rest of the images), works in `<img>` tags and can be cached forever because a new upload gets a new id. The user URL is guessable (sequential ids), so it requires login, and its content changes when the avatar is replaced, so it is sent with `no-cache`. The trade-off is that anyone who obtains an avatar's UUID can see that picture without logging in; avatars are not sensitive data, and the UUID is only given to logged-in users |
| Oct 2026 | A trip is readable and editable only by its creator; 404 is checked before 403, in the service (`findTripForRead` / `findTripForWrite`)                                                                                                                                           | Checking ownership in the controller; answering 404 for another user's trip                                                      | The two methods are the only place to extend when participants (I3) and trip moderation by the administrator (B8) arrive; a missing trip is reported as missing to anyone                                                                                                                                                                                                                                                                                                                                                            |
| Oct 2026 | The administrator gets 403 on other users' trips until trip moderation (B8) exists                                                                                                                                                                                                | Letting the administrator read and delete any trip now                                                                           | "User permissions" gives that power to the moderation feature, not to trip management                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Nov 2026 | The administrator can read and delete any trip (B8) but never edit it: `findForRead` and `findForDelete` accept the `ADMIN` role, `findForWrite` stays creator-only                                                                                                               | One `findForWrite` that lets the administrator through; an admin-only delete endpoint                                            | Moderation is reviewing and removing. Editing another user's trip or activities would change their content. The rule stays in `TripAccessService`, and the existing endpoints and the cascade of B4/B5 are reused                                                                                                                                                                                                                                                                                                                    |
