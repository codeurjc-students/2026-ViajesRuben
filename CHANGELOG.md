# Changelog

All notable changes to the **TripMate** project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- I7: publishing and unpublishing of trips. `Trip` gets `published` (false by default) and `publishedAt`, and `TripDTO` reports both. `PUT /api/v1/trips/{id}/publication` with `{"published": true|false}` publishes or unpublishes the trip; only the creator may publish (403 for another user and for the administrator; unpublishing is opened to the administrator by I10), it is idempotent, and publishing sets `publishedAt` once, so publishing a published trip keeps the first date.
- I7: the trip page has a "Publicar" / "Despublicar" button for the creator, and a "Público" badge appears on published trips there and on the cards of "Mis viajes".
- I7: the home page carousel shows the public itineraries of any user, with the author's name on each card, three at a time and at most the nine most recently published. A "Ver todos" link next to its title goes to `/public`, the public itineraries page (I8).
- I7: sample data publishes five trips of three authors (the administrator's three, Ana's Lisbon and Carlos's Andalusia), so the carousel shows several authors.
- I8: public itineraries page at `/public`, open to anyone: the complete list of published trips, newest publication first, ten at a time with a "Más resultados" button, one line per trip (name, destination, dates and author) linking to its read-only preview, and a search by trip name or destination (on submit, ignoring case). It has empty states for no public trips and for a search without results. A "Viajes públicos" link in the header, for anonymous and logged-in users, opens it.
- I8: `GET /api/v1/trips/public` accepts an optional `search` parameter that keeps the published trips whose name or destination contains the text, ignoring case and surrounding spaces; blank lists all. The sort, page size, public DTO (no emails) and the public URLs are unchanged, and the search is done in the database query.
- I10: moderation of public itineraries. The administrator may unpublish any trip with the existing `PUT /api/v1/trips/{id}/publication` and `{"published": false}`: the trip leaves the public list and the carousel, and its creator keeps it, unpublished. Publishing another user's trip is still 403 for the administrator, and another regular user still gets 403 on both; the decision is `TripAccessService.findForUnpublish` (creator or administrator, 404 before 403). The log line of a publication change now carries the trip, its creator and the user who changed it.
- I10: the administrator sees a "Despublicar" button on every row of the public itineraries page and on the public preview, with a confirmation ("Dejará de ser público; el viaje no se borra."). After it the list reloads, or the preview goes back to `/public`, with a notice. Nothing changes for other users.
- I9: copy a public itinerary to one's own account. `POST /api/v1/trips/public/{id}/copies` (login required; 401 for a visitor, 404, never 403, for a trip that is not published) creates a new trip of the user with the same name, destination, budget and description, not published, plus a copy of its cover and of its activities (the user is their author), and answers 201 with the new trip in the body and its URL in `Location`. The optional body `{"startDate": "yyyy-MM-dd"}` makes the copy start that day, keep the length of the trip and move every activity by the same number of days; without it the original dates are kept. Every image is duplicated as a new row, so the copy never shares data with the original, and everything happens in one transaction.
- I9: `Trip` gets `copiedFrom` (column `copied_from_id`, null for a trip that is not a copy) and `TripDTO` reports it as `copiedFromId`. Deleting the original sets `copiedFromId` to null on its copies (an explicit update before the delete, no database cascade), so a copy keeps working.
- I9: the public itinerary page (`/public/:tripId`) has a "Copiar en tu cuenta" button. A visitor is sent to the login page and brought back to the same itinerary; a logged-in user chooses an optional new start date in a modal and lands on the new trip, with a message that it was copied.

- I1: the creator of a trip invites people by email. New `Invitation` entity (trip, inviter, invited email, optional invited account, status `PENDING`, `sentAt` and a random token of 32 bytes that is unique and never returned by the API). `POST /api/v1/trips/{tripId}/invitations` with `{"email": "..."}` answers 201 with `Location` and the invitation; `GET /api/v1/trips/{tripId}/invitations` lists them, ten at a time and newest first (`sort` accepts `id`, `invitedEmail`, `status` and `sentAt`), and `GET /api/v1/trips/{tripId}/invitations/{id}` reads one. Only the creator may use them (403 for another user and for the administrator, 401 for a visitor, 404 before 403 for an unknown trip). The email is trimmed and lower cased like at registration, and it may have no account yet (that person registers and answers in I2). A second pending invitation for the same email and trip is a 409 and the creator's own email is a 400. `InvitationService.ensureNotMember` is the single place where I2 adds the check for people who already take part in the trip.
- I1: the invited person receives an email in Spanish with who invites, which trip and a link `{APP_PUBLIC_URL}/invitations/{token}`. It is sent in the background after the invitation transaction commits (`@TransactionalEventListener(AFTER_COMMIT)` with `@Async`, from an `InvitationCreatedEvent` with plain data), so an invitation that is rolled back sends nothing and a failed email never undoes the invitation. A failure is logged with the invitation number and the kind of error, never the address or the token, and the email is not retried. The sending is in its own `notification` package so it can become a separate service later. New settings, all environment variables with defaults: `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_SMTP_AUTH`, `MAIL_SMTP_STARTTLS`, `MAIL_FROM` and `APP_PUBLIC_URL`.
- I1: the trip page shows the creator an "Invitaciones" section with a form ("Invitar por email" and "Enviar invitación", validated in the client and disabled while sending, with the API errors shown inline) and the list of invitations with their date and a "Pendiente" badge, ten at a time. The administrator reviewing a trip does not see it. `/invitations/:token`, the link of the email, is a public placeholder page until I2.
- I1: Compose files start Mailpit (`axllent/mailpit`), a test inbox that catches the emails of the application, at http://localhost:8025; nothing reaches a real address by default. `docs/execution.md` explains the email settings and how to send real emails with Gmail (a dedicated account, 2-step verification, an app password and a `.env` file), and that the links only work from other devices when `APP_PUBLIC_URL` is a public address. `.gitignore` now ignores `.env` and `.env.*`.

- I2: the invited person accepts or rejects an invitation. New `Participation` entity (trip, user, `joinedAt`, unique per trip and user) in a new `participation` package; `Invitation` gets `respondedAt` and the statuses `ACCEPTED` and `REJECTED` (`InvitationDTO`, the creator's view, reports both). Only the logged-in user whose normalised email matches the invited email may answer (403 for anyone else, the creator and the administrator included; 401 for a visitor). An invitation is answered once (409), a trip deleted meanwhile is a 404, and accepting makes the user a participant and remembers their account on the invitation, in one transaction. Invitations do not expire: they stay valid until answered or until their trip is deleted.
- I2: new endpoints. `GET /api/v1/invitations` lists the pending invitations of the logged-in user, ten at a time and newest first (`sort` accepts `id` and `sentAt`); `GET /api/v1/invitations/token/{token}` is what the link of the email opens, in any status and only for its addressee; `PUT /api/v1/invitations/{id}/status` with `{"status": "ACCEPTED" | "REJECTED"}` answers. They return `ReceivedInvitationDTO` (trip id and name, inviter's name, status and dates), never the email, the token or user ids. Inviting someone who already participates in the trip is now a 409 (`InvitationService.ensureNotMember`).
- I2: participants read the trip. `TripAccessService.findForRead` accepts the creator, the administrator and the participants, so they can read the trip, its cover, its activities, their pictures, the cost and the conflicts; editing, publishing, inviting and deleting stay creator-only (and deleting also for the administrator), and `GET /api/v1/trips` lists the trips the user created or joined, with the paging and sorting done in the query. Deleting a trip deletes its participations first.
- I2: `/invitations/:token` is now the invitation page and needs a login: a visitor is sent to log in or register and brought back to it. It shows who invites to which trip with "Aceptar" and "Rechazar" (accepting goes to the trip), and says so when the invitation was already answered, was sent to another account, or does not exist any more. The page asks browsers not to send the token as a referrer.
- I2: "Mis viajes" shows an "Invitaciones pendientes" section, only when there are any, with "Aceptar" and "Rechazar" on each one; accepting adds the trip to the list. The creator's invitation list shows "Pendiente", "Aceptada" and "Rechazada", and a participant sees the trip without any edit, delete, publish or invite button.

- I3: the creator manages the participants of a trip and a participant can leave it. `GET /api/v1/trips/{tripId}/participants` lists who joined, ten at a time and oldest first (`sort` accepts `id` and `joinedAt`), for anyone who can read the trip (the creator, the participants and the administrator): each entry has `userId`, `name`, `avatarId` (a UUID, null without picture) and `joinedAt`, and the `email` only for the trip's creator, null for everyone else. The creator is not listed. The page is one query that projects into `ParticipantDTO`, so it pages and sorts in the database.
- I3: `DELETE /api/v1/trips/{tripId}/participants/{userId}` answers 204. The creator removes any participant and a participant can only remove themselves (leaving); anyone else gets 403 (another participant, the administrator, a stranger, or a user already removed), a visitor 401, an unknown trip or a user who is not a participant 404, and the creator's own id is a 409 ("The creator cannot leave the trip; delete it instead"). The checks run in the order 404, 403, 409, 404, decided by the new `TripAccessService.findForParticipantRemoval`; the operations are in the new `ParticipantService`. The effect is immediate: the removed user's next request to the trip is 403 and the trip leaves their "Mis viajes". Only the participation is deleted: the invitation stays `ACCEPTED` as history and the person can be invited again.
- I3: the trip page has a "Participantes" section for the creator and the participants (the administrator reviewing a trip does not see it): avatar, name ("(tú)" for oneself), join date and, for the creator only, the email, ten at a time with "Más resultados". The creator has "Quitar" on each one, with a confirmation; a participant has "Salir del viaje", with a confirmation, and goes back to "Mis viajes" with the notice "Has salido de «…»." (a dismissible alert, now supported by that page).
- I3: every trip has a `participantCount` (in `TripDTO`, so the list, the single trip, the creation, the update, the publication and the copy all report it): how many people joined the trip, not counting its creator, as in the list of participants. The list of `GET /api/v1/trips` gets the counts of the whole page with one grouped query (`ParticipationRepository.countByTripIds`), not one per trip, and the other endpoints use a plain count; a new or copied trip is 0. The cards of "Mis viajes" show it as "Participantes: N", to the creator and to the participants alike.
- Documentation: `docs/api/api-docs.yaml` and `api-docs.html` were regenerated and now include the I2 endpoints (`/api/v1/invitations`, `/api/v1/invitations/token/{token}`, `/api/v1/invitations/{id}/status`), which the committed specification did not have, and the I3 ones; the Postman collection has the two I3 requests with their examples.

- I4: collaborative itinerary with a change log. The creator and the participants create, edit and delete any activity of the trip and its picture (the first analysis limited participants to their own activities; this was decided by the author of the project and is explained in `docs/analysis.md`). New `ActivityLogEntry` entity (trip, activity, activity name, user, user name, action `CREATED`, `UPDATED` or `DELETED`, changed fields and time) and a new `ActivityLogService` that writes one line for every creation, edit, deletion and picture change, in the same transaction as the change, so a change that fails leaves no line. An edit lists the names of the fields that really changed (`name`, `description`, `location`, `date`, `startTime`, `endTime`, `cost`, `category`, `image`), never their values; an edit that changes nothing writes its line with no fields, and removing a picture that is not there writes nothing.
- I4: `GET /api/v1/trips/{tripId}/activity-log` lists the log of a trip, newest first and ten at a time (`sort` accepts `id` and `createdAt`; another property is a 400), for anyone who can read the trip (the creator, the participants and the administrator; 403 for anyone else, 401 for a visitor, 404 for an unknown trip). The names of the activity and of the user are copies, and `activityId` is null once the activity is deleted, so a line keeps reading the same. Removing a participant keeps their activities and their lines.
- I4: every activity has `authorName` (`ActivityDTO`), read in the same query as the activities. A public itinerary returns it as null, so it never names the members of the trip.
- I4: the trip page shows the creator and the participants "Nueva actividad", "Editar" and "Eliminar" on every activity, and each activity says who added it ("Añadida por ..."). The conflict warnings (B6) give them the "Editar" links too. The administrator reviewing a trip still sees it read-only.
- I4: the trip page has a compact "Historial de cambios" section below the itinerary, for everyone who opens the trip: the 5 latest lines ("Laura editó «Visita al museo» · hace 2 h", with the changed fields in a smaller second line and the exact time in a tooltip), "Ver más" for 10 more (loading the next page when needed), "Ver menos" to go back to 5, "Aún no hay cambios" when there are none, and it is read again after an activity is deleted there.
- Documentation: `docs/api/api-docs.yaml` and `api-docs.html` were regenerated with the I4 endpoint and `authorName`, the Postman collection has a request and examples for the change log, and the descriptions of the activity requests say who may use them now.

- I5: spending charts on the trip page. `GET /api/v1/trips/{tripId}/activities/spending` (the creator, a participant or the administrator; 400, 401, 403, 404) returns the trip's budget (`null` without one), the total cost, the cost per category (the biggest first; `category: null` groups the activities without one) and the cost per day with its running sum. Both sums are `SUM ... GROUP BY` queries in the database and ignore the activities without cost; the days without cost are filled in with 0 by the service (`ActivityService.fillDays`), which also includes a day outside the trip's dates that has cost, so the last running sum is always the total. `GET .../activities/cost` is unchanged.
- I5: the trip page has a "Gastos" section after the itinerary, for the creator and the participants (not for the administrator reviewing a trip, nor in the public itinerary): a bar chart of the spending by category with the total against the budget ("Gastado X de Y", a progress bar and "Presupuesto superado" when it goes over), and a line chart of the cumulative spending over every day of the trip with the budget as a reference line. Amounts are in euros and texts in Spanish; a trip without costs says "Aún no hay gastos"; each chart has a visually hidden table with the same figures for screen readers; it is responsive; and it is read again after an activity is deleted on the page.
- I5: the charts are drawn with [Recharts](https://recharts.org/) 3.10.1 (pinned, no `^`), which renders SVG, so the tests read the bars and lines in the DOM.
- Documentation: `docs/api/api-docs.yaml` and `api-docs.html` were regenerated with the I5 endpoint, the Postman collection has a request and examples for it, `docs/functionalities.md` marks I5 as implemented and `docs/development-guide.md` documents the feature, its tests and its decisions.

- I6: platform metrics dashboard. `GET /api/v1/admin/metrics` (administrator only: 401 for a visitor, 403 for a regular user) answers `{"users", "trips", "activities"}`. Each total is one `COUNT` in the database, read by the new `MetricsService` (new `metrics` package) with `UserRepository.countByRole` and the `count()` of the trip and activity repositories. Users are the regular accounts, blocked ones included and the administrator not; trips include the unpublished ones. It is not paginated, and the AI requests are not included: they arrive in version 1.0.
- I6: `/admin` is no longer a placeholder. "Panel de administración" shows the three totals in cards ("Usuarios", "Viajes", "Actividades", one column on a phone), links to "Gestionar usuarios" and "Moderar viajes", a spinner while loading and the shared error page when the totals cannot be read. The header has a "Panel" link for the administrator.
- I6 tests: backend unit, integration (real MySQL, with blocked users and unpublished trips) and REST API tests (401, 403, known data, exact changes after registering, creating and deleting), frontend unit and client – server integration tests, and a Selenium flow (the administrator opens the panel and sees the totals, the links work, a regular user gets the no-access page, the cards fit a phone).
- Documentation: `docs/api/api-docs.yaml` and `api-docs.html` were regenerated with the I6 endpoint, the Postman collection has a request and examples for it, `docs/functionalities.md` marks I6 as implemented and `docs/development-guide.md` documents the feature, its tests and its decisions.

### Changed

- I4: creating, editing and deleting activities, and uploading or deleting their pictures, are decided by `TripAccessService.findForItineraryWrite` (the creator or a participant, 403 for the administrator and anyone else) instead of `findForWrite`, which stays creator-only for the trip itself, its cover, its publication and its invitations.
- I4: deleting a trip deletes its change log first (an explicit delete, before its activities), and deleting an activity detaches its log lines before it is deleted.
- I4: `docs/functionalities.md` and `docs/analysis.md` describe the new rule and the new entity, and `docs/development-guide.md` documents the feature, its decisions and a known limitation: two members who edit the same activity at the same time do not warn each other, the last save wins and both changes appear in the log (optimistic locking could be added later).
- I1: deleting a trip deletes its invitations first (an explicit delete, before its activities).
- Planned features for version 0.2 extended with public itineraries (I7–I10): publishing trips, the public itineraries page, copying an itinerary to one's account and administrator moderation; the example itineraries of B1 become public itineraries.
- I7: the example trips become public trips. `GET /api/v1/trips/examples`, `/examples/{id}` and `/examples/{id}/activities` are now `GET /api/v1/trips/public`, `/public/{id}` and `/public/{id}/activities`, they return the published trips of any user (newest publication first by default; `sort` also accepts `publishedAt`), and a trip that is not published is a 404, never a 403. The public answers carry `authorName` and never an email, an author id or participants. The old URLs are gone (401), and `SecurityConfig` lists the new exact paths. The frontend route `/examples/:tripId` is now `/public/:tripId`.
- I7: the sample data publishes a trip only when it creates it, so a trip somebody unpublished stays unpublished after a restart.

### Upgrading an existing development database

- The schema is still updated by Hibernate (no Flyway): `trip.published` (not null, default false) and `trip.published_at` are added on start-up, so existing trips start unpublished and nothing breaks. The sample trips are published only when they are created, so an existing development database does not get the published sample trips until it is reset (delete the `tripmate-mysql` container and create it again, or drop the `tripmate` schema); until then the home carousel is empty, and a user can publish their own trips from the trip page.
- `trip.copied_from_id` (nullable, a foreign key to `trip.id`) is added on start-up (I9); no existing row changes, because no existing trip is a copy.
- I5 adds no table or column: the charts read the existing `activity` rows, so nothing changes in an existing database.
- I6 adds no table or column either: the totals count the existing `user`, `trip` and `activity` rows.
- The new `activity_log_entry` table (I4) is created on start-up; it only points at existing trips, activities and users, so nothing existing changes (the log of an existing trip starts empty).
- The new `invitation` table (I1) is created on start-up; it only points at existing trips and users, so nothing existing changes.
- The invitation emails need an SMTP server. Without configuration the application sends them to `localhost:1025` (a test inbox such as Mailpit); if nothing listens there the invitations are still created and the failure is only logged. See `docs/execution.md`.

## [0.1.0] - 2026-11-04

First GitHub release (tag `0.1`): the basic functionality B1–B8, the Docker image and continuous delivery.

### Added

- Documentation of version 0.1: a README with the summary of the version, screenshots, video and the next versions; the features page with the version 0.1 screens and the implementation status of every feature; `docs/execution.md` (requirements, running a published version, sample data, with and without sample data, deployment on an external server); and the development guide updated with the types of tests, the traceability between tests and features, the test statistics, the code size and the development process.
- Security base with Spring Security: login (`POST /api/v1/auth/login`), logout (`POST /api/v1/auth/logout`) and current user (`GET /api/v1/auth/me`) with a JWT stored in an `HttpOnly`, `Secure`, `SameSite=Strict` cookie.
- `User` entity with roles (`USER`, `ADMIN`) and status (`ACTIVE`, `BLOCKED`); blocked users cannot log in, and a user blocked after logging in is rejected on the next request.
- Single administrator defined in the configuration (`ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD_HASH` with a BCrypt hash) and synchronized into the database on start-up.
- Access rules: `/api/v1/admin/**` requires the administrator, and the rest of `/api/**` requires a logged-in user, except login, logout, registration, reading an image and the public example trips (`GET /api/v1/trips/examples/**`).
- Common JSON error body (`timestamp`, `status`, `error`, `message`, `path`) for validation and security errors.
- HTTPS on port 443 with a self-signed development keystore; port, keystore and token settings are configurable with environment variables.
- Tests for the security base: backend unit, integration and REST API system tests.
- `ResourceNotFoundException` (404) and `ConflictException` (409), and `GET /api/v1/trips/{id}` (404 JSON error for an unknown trip).
- Images stored in the database: `POST /api/v1/images` (logged-in users; JPEG, PNG or WebP up to `IMAGE_MAX_SIZE`, validated by type and file signature; 201 with `Location`) and public `GET /api/v1/images/{id}` with `Content-Type` and cache headers. `Image` ids are UUIDs.
- Frontend `ImageUpload` and `StoredImage` components and the `DEFAULT_TRIP_COVER` fallback image.
- Error handling for invalid images (400), too large uploads (413) and missing multipart parts (400).
- Pagination contract: `PageDTO` (`content`, `page`, `size`, `totalElements`, `last`), `?page=&size=` (10 per page by default, 50 at most) and the reusable `usePagedList` hook and "Más resultados" button in the frontend.
- Sample data now has 12 trips and is enabled with `SAMPLE_DATA` (`app.sample-data.enabled`); trips that are missing are added on start-up.
- Shared error page (same layout) for unknown routes (404), server errors (5xx) and no connection, with a button back to the home page.
- Error handling for malformed JSON and wrong parameter types (400), unsupported methods (405), unknown URLs (404) and unexpected errors (500, logged, without details in the response).
- The React application is served by Spring Boot over HTTPS: client routes such as `/trips` return `index.html` (also after a page refresh), unknown `/api/**` URLs keep returning the JSON 404 and missing files return 404.
- Docker image (`docker/Dockerfile`, multi-stage: Node build of the frontend, Maven build of the jar, JRE 21 runtime with a non-root user listening on port 443) and `.dockerignore`.
- Docker Compose files `docker/docker-compose.yml` (image `rubenruiz7/tripmate:0.1.0`) and `docker/docker-compose-dev.yml` (image `rubenruiz7/tripmate:dev`) with the application and MySQL, configured with environment variables that have defaults.
- Docker deployment documentation in the development guide.
- Continuous delivery with GitHub Actions: a reusable workflow builds and pushes the image `rubenruiz7/tripmate:<tag>` and publishes the Compose file as the OCI artifact `rubenruiz7/tripmate-compose:<tag>` to DockerHub. A push to `main` publishes `dev`, a published release `x.y.z` publishes `x.y.z` and `latest` (after checking that the commit is on `main` and passed Basic quality), and a manual run publishes `<branch>-<date>-<commit>`.
- Documentation of continuous delivery and versioning in the development guide, and instructions in the README to run the application from the OCI artifact.
- B2: user registration (`POST /api/v1/users`: 201 with `Location`, 400 for invalid data, 409 for a taken email or the administrator email; the new user is always a regular user and the password is stored hashed).
- B2: `/login` and `/register` pages with client-side validation and inline error messages, an authentication context (`/api/v1/auth/me` on load, login, logout, register), a header that shows the login and register links or the user name and "Cerrar sesión", and automatic login after registering.
- B2: private routes redirect anonymous visitors to `/login` and return them to the page they asked for after logging in.
- B2 tests: backend unit, integration and REST API tests, frontend unit and client – server integration tests, and a Selenium flow (register, log out, log in).
- B3: own profile in the API, only for the user themselves (`GET` and `PUT /api/v1/users/{id}`: 403 for another user, 404, 409 for a taken email or the administrator email). Changing the email does not log the user out, because the token identifies the user by id.
- B3: password change (`PUT /api/v1/users/{id}/password`), which requires the current password (400 if it is wrong) and follows the 8–72 character rule.
- B3: avatar stored in the database (`PUT`, `GET` and `DELETE /api/v1/users/{id}/avatar`), validated like any other image; replacing or deleting it deletes the previous image. Users without avatar show the initial of their name.
- B3: `/profile` page with view and edit mode for the name and email, a separate form to change the password, and the avatar with upload, replace and delete. The header shows the avatar and name, links to `/profile` and is updated without reloading.
- B3: the administrator's profile is read-only except for the avatar, because its details come from the configuration.
- B3 tests: backend unit, integration and REST API tests, frontend unit and client – server integration tests, and a Selenium flow (register, edit the name, change the avatar and the password, log out, log in with the new password).
- B4: every trip has a creator. Own trips can be created, read, edited and deleted (`POST /api/v1/trips` 201 with `Location`, `GET`, `PUT` and `DELETE /api/v1/trips/{id}`), and only the creator can use them: 403 for another user's trip, 404 for a missing one, 400 for invalid data (required name, destination and dates; the end date cannot be before the start date; optional budget and description with limits).
- B4: trip cover stored in the database (`PUT`, `GET` and `DELETE /api/v1/trips/{id}/cover`), validated like any other image; replacing or deleting it, or deleting the trip, deletes the previous image. Trips without cover show the default image.
- B4: `GET /api/v1/trips` can be sorted only by `id`, `name`, `destination`, `startDate`, `endDate` and `createdAt` (400 otherwise).
- B4: sample data now has three users (`ana@tripmate.com` with 12 trips, `carlos@tripmate.com` with 3 and `laura@tripmate.com` with 2, all with the password `Demo-2026`, which `SAMPLE_USERS_PASSWORD` can change), documented in the README and the development guide.
- B4: `/trips` ("Mis viajes") with "Nuevo viaje", `/trips/new`, `/trips/:id` and `/trips/:id/edit`. One form creates and edits a trip, with the cover chosen and previewed before saving; the trip page shows the cover and details and offers "Editar" and "Eliminar" to the creator; deleting asks for confirmation in a dialog; the list reloads after a deletion.
- B4: the confirmation dialog (`ConfirmModal`), the select-only mode of `ImageUpload`, the `useTrip` hook and `usePagedList.reload`; the error page explains 403 and 401.
- B4 tests: backend unit, integration and REST API tests (a negative case for every endpoint), frontend unit and client – server integration tests, and a Selenium flow as a sample user (create a trip with a cover, see it in the list, edit it, delete it).
- Known limitation documented: database schema changes need Flyway migrations after 0.1.0.
- B5: the activities of a trip's itinerary at `/api/v1/trips/{tripId}/activities`: `GET` (paginated, sorted by date and start time, filtered by day with `?date=yyyy-MM-dd`) and `POST` (201 with `Location`), and `GET`, `PUT` and `DELETE /api/v1/trips/{tripId}/activities/{activityId}`.
